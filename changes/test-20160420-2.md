## INSTALL-01 — Venv roto tras actualización de Python

**Severidad:** Alta (bloqueante)  
**Componente:** Entorno Python / `.venv`  
**Síntoma observado:**

```
dyld[53261]: Library not loaded: @rpath/libpython3.11.dylib
  Referenced from: /path/to/meridian/.venv/bin/python3
  Reason: tried: '/path/to/meridian/.venv/lib/libpython3.11.dylib' (no such file)
```

**Causa raíz:**

El `.venv` de Meridian fue creado con Python 3.11 administrado por `uv`. Al actualizar el sistema (OS o la instalación de Python), la librería dinámica `libpython3.11.dylib` quedó en una ruta diferente o fue eliminada. El `.venv` mantiene hardcoded el RPATH del intérprete original, por lo que falla al cargar aunque Python 3.11 siga disponible vía `uv`.

Este problema **no se detecta hasta intentar ejecutar el servidor** — `uv run` falla silenciosamente desde el punto de vista de Claude Code (el proceso termina con señal SIGABRT antes de leer stdin).

**Fix inmediato (usuario):**

```bash
cd /path/to/meridian
rm -rf .venv
uv sync
```

**Fix estructural (equipo de desarrollo):**

1. **Agregar comprobación de salud del venv en el arranque del servidor:**

```python
# src/meridian/__main__.py — antes de iniciar el servidor MCP
import sys

def check_python_environment() -> None:
    """Verifica que el intérprete Python tenga acceso a las dependencias críticas."""
    try:
        import sqlite3
        import fastmcp
    except ImportError as e:
        print(f"ERROR: Entorno Python incompleto — {e}", file=sys.stderr)
        print("Ejecuta: uv sync", file=sys.stderr)
        sys.exit(1)
```

2. **Documentar en README el procedimiento de recuperación:**

Agregar sección `## Troubleshooting` con el paso de `rm -rf .venv && uv sync` como primer remedio ante cualquier error de arranque.

3. **Agregar `pyproject.toml` → `requires-python = ">=3.11"` ya existe.** Verificar que `uv` esté configurado para usar la versión administrada por él mismo (`uv python pin 3.11`) en lugar de la del sistema, para evitar que actualizaciones del SO afecten el venv:

```bash
# En el directorio del proyecto, después de clonar:
uv python pin 3.11
uv sync
```

## INSTALL-02 — MCP no carga desde `settings.json` en Claude Code

**Severidad:** Alta (bloqueante)  
**Componente:** Configuración de Claude Code  
**Síntoma observado:**

El servidor Meridian fue configurado correctamente en `~/.claude/settings.json` bajo la clave `mcpServers`, pero **ningún tool de Meridian aparecía disponible** en sesiones de Claude Code nuevas. `claude mcp list` no mostraba el servidor.

**Causa raíz:**

Claude Code utiliza **dos archivos de configuración con responsabilidades distintas**:

| Archivo | Propósito | Carga MCP servers |
|---------|-----------|:-----------------:|
| `~/.claude/settings.json` | Configuración del agente: permisos, plugins, hooks, env vars | **No** |
| `~/.claude.json` | Configuración del cliente CLI: MCP servers, preferencias de sesión | **Sí** |

La documentación del README de Meridian indica usar `~/.claude/settings.json`, lo cual es incorrecto para la versión actual de Claude Code. El archivo correcto es `~/.claude.json`, y la forma canónica de registrar un server es mediante el CLI:

```bash
claude mcp add -s user \
  -e KNOWLEDGE_BASE_PATH=/path/to/meridian-kb \
  -e MERIDIAN_ACCESS_LEVEL=write \
  -- meridian \
  /path/to/meridian/.venv/bin/python \
  -m meridian mcp
```

Este comando escribe en `~/.claude.json` bajo la clave `mcpServers`.

**Fix en README:**

Reemplazar la sección `### Claude Code` en `## MCP Configuration` con las instrucciones correctas:

```markdown
### Claude Code

**Método recomendado — CLI (escribe en `~/.claude.json`):**

```bash
claude mcp add -s user \
  -e KNOWLEDGE_BASE_PATH="$HOME/meridian-kb" \
  -e MERIDIAN_ACCESS_LEVEL=write \
  -- meridian \
  /absolute/path/to/meridian/.venv/bin/python \
  -m meridian mcp
```

Verifica la conexión:

```bash
claude mcp list
# meridian: /path/to/.venv/bin/python -m meridian mcp - ✓ Connected
```

**Nota:** No uses `~/.claude/settings.json` para registrar MCP servers — ese archivo controla
permisos y hooks del agente, no la lista de servidores MCP.
```

**Impacto adicional:** El README indica `"MERIDIAN_ACCESS_LEVEL": "analyze"` como valor en el ejemplo de `settings.json`. Para que los skills `/update-global-rules` y `/pr-lessons` funcionen correctamente en Claude Code, el nivel debe ser `write`. Corregir el ejemplo a `write` y agregar una nota aclarando cuándo usar cada nivel.

## INSTALL-03 — Comando `uv` no resuelto en el PATH de Claude Code

**Severidad:** Alta (bloqueante)  
**Componente:** Resolución de PATH en el proceso MCP  
**Síntoma observado:**

Incluso después de corregir el archivo de configuración a `~/.claude.json`, al usar `"command": "uv"` o `"command": "/Users/<user>/.local/bin/uv"` el servidor no respondía al healthcheck de Claude Code, dejando el entry de `claude mcp list` sin aparecer.

**Causa raíz:**

Claude Code lanza el proceso MCP con un entorno de shell reducido que **no hereda el `PATH` completo del usuario**. `uv` instalado en `~/.local/bin/` (instalación estándar de `uv` en macOS/Linux) no está en el PATH del proceso hijo que Claude Code crea para el servidor MCP.

El problema se manifiesta en dos variantes:

1. `"command": "uv"` → `ENOENT` — el ejecutable no se encuentra en el PATH reducido.
2. `"command": "/Users/<user>/.local/bin/uv"` → El proceso inicia pero `uv run --directory ...` necesita resolver el Python y las dependencias, lo que puede generar latencias o fallos silenciosos si `uv` no puede acceder a su cache.

**Fix recomendado (más robusto):**

Usar el ejecutable Python del `.venv` directamente, evitando la dependencia de `uv` en tiempo de ejecución del servidor:

```json
{
  "command": "/absolute/path/to/meridian/.venv/bin/python",
  "args": ["-m", "meridian", "mcp"]
}
```

Este enfoque es:
- Independiente de la ubicación de `uv` en el PATH
- Sin overhead de resolución de dependencias en cada arranque
- Más rápido (el venv ya está construido)

**Fix en README:**

Actualizar todos los ejemplos de configuración para usar el Python del `.venv` en lugar de `uv run`:

```markdown
### Opción A — Python del venv (recomendado para Claude Code)

```bash
claude mcp add -s user \
  -e KNOWLEDGE_BASE_PATH="$HOME/meridian-kb" \
  -e MERIDIAN_ACCESS_LEVEL=write \
  -- meridian \
  "$PWD/.venv/bin/python" \
  -m meridian mcp
```

### Opción B — uv run (requiere que uv esté en PATH del proceso hijo)

```bash
claude mcp add -s user \
  -e KNOWLEDGE_BASE_PATH="$HOME/meridian-kb" \
  -e MERIDIAN_ACCESS_LEVEL=write \
  -- meridian \
  /absolute/path/to/uv \
  run --directory /absolute/path/to/meridian \
  python -m meridian mcp
```

> **Nota macOS/Linux:** Si Claude Code no encuentra `uv`, usa la Opción A.
> Verifica la ruta de `uv` con `which uv`.
```

## INSTALL-04 — Error de threading SQLite con FastMCP stdio

**Severidad:** Alta (bloqueante — primer error funcional post-conexión)  
**Componente:** `src/meridian/db/connection.py`  
**Síntoma observado:**

Una vez conectado el servidor, **cualquier invocación de tool** retornaba:

```
Error calling tool 'query_rules': SQLite objects created in a thread can only 
be used in that same thread. The object was created in thread id 8430328000 
and this is thread id 6106918912.
```

Los tres tools probados simultáneamente (`query_rules`, `query_lessons`, `get_project_scope_resolution`) fallaban con el mismo error.

**Causa raíz:**

El flujo de arranque en `server.py:run_stdio()` es:

```python
def run_stdio() -> None:
    init_db()          # ← crea sqlite3.Connection en el hilo principal (thread A)
    mcp.run(transport="stdio")  # ← FastMCP despacha tool handlers en thread pool (thread B, C, ...)
```

`init_db()` crea la conexión SQLite y la almacena como variable global `conn`. SQLite, por defecto, lanza `ProgrammingError` si el objeto `Connection` se usa desde un hilo diferente al que lo creó (`check_same_thread=True` es el default). FastMCP utiliza un thread pool para despachar las llamadas a tools concurrentemente, por lo que el hilo que llama a `_get_conn()` dentro de un tool handler **nunca es el hilo principal**.

**Fix aplicado en esta sesión:**

```python
# src/meridian/db/connection.py
def get_connection(db_path: Path) -> sqlite3.Connection:
    conn = sqlite3.connect(str(db_path), check_same_thread=False)  # ← fix
    conn.execute("PRAGMA journal_mode=WAL")
    conn.execute("PRAGMA foreign_keys=ON")
    return conn
```

`check_same_thread=False` es seguro porque:
- El modo WAL (`journal_mode=WAL`) está activado, lo que permite lecturas concurrentes sin bloqueo.
- SQLite en modo WAL es thread-safe para múltiples lectores simultáneos y serializa las escrituras internamente.
- La única operación de escritura concurrente en el contexto MCP es el log de auditoría (`access_log`), que es append-only.

**Fix alternativo para mayor aislamiento (recomendado para v0.2):**

En lugar de compartir una conexión global, usar conexiones por hilo con `threading.local()`:

```python
import threading
from pathlib import Path
import sqlite3

_local = threading.local()

def get_connection(db_path: Path) -> sqlite3.Connection:
    """Retorna una conexión SQLite por hilo, creándola si no existe."""
    if not hasattr(_local, "conn") or _local.conn is None:
        _local.conn = sqlite3.connect(str(db_path))
        _local.conn.execute("PRAGMA journal_mode=WAL")
        _local.conn.execute("PRAGMA foreign_keys=ON")
    return _local.conn
```

Este enfoque elimina el state compartido entre hilos y es más robusto si FastMCP cambia su modelo de concurrencia en versiones futuras.

**Test de regresión requerido:**

```python
# tests/test_threading.py
import threading
from meridian.db.connection import get_connection
from meridian.config import get_db_path
from meridian.tools.knowledge_consumption import query_rules

def test_concurrent_tool_calls_do_not_raise_threading_error(tmp_path):
    """Simula el patrón de FastMCP: conexión creada en hilo A, usada en hilo B."""
    db_path = tmp_path / "test.db"
    # Inicializar en hilo principal
    from meridian.db.connection import initialize_db
    initialize_db(db_path)
    conn = get_connection(db_path)

    errors = []

    def call_from_thread():
        try:
            query_rules("psp-integrator", conn=conn)
        except Exception as e:
            errors.append(e)

    t = threading.Thread(target=call_from_thread)
    t.start()
    t.join()

    assert not errors, f"Threading error: {errors[0]}"
```

## INSTALL-05 — Directorios `global` del KB ausentes tras instalación

**Severidad:** Media  
**Componente:** Estructura del Knowledge Base / `README.md`  
**Síntoma observado:**

Tras ejecutar los comandos de instalación del README, la estructura del KB quedó incompleta:

```bash
$ ls ~/meridian-kb/knowledge-base/
projects/          # ← solo este directorio existía

$ ls ~/meridian-kb/lessons/
projects/          # ← solo este directorio existía
```

Los directorios `knowledge-base/global/` y `lessons/global/` no fueron creados, lo que causa:

1. `index_rules_from_markdown` con `default_scope_id='global-quarkus'` falla al intentar escribir el archivo de destino.
2. `approve_proposal` para cualquier regla de scope global falla con `FileNotFoundError` porque el archivo `.md` destino no existe.

**Causa raíz:**

Los comandos de creación de directorios del README son correctos, pero el proceso de `uv pip install -e ".[dev]"` (paso de instalación) no crea la estructura del KB automáticamente. Si el usuario crea el directorio raíz (`~/meridian-kb`) y luego ejecuta `initialize_db()` antes de crear los subdirectorios, la DB se inicializa correctamente pero los archivos `.md` destino nunca se crean.

El README presenta los pasos en orden correcto, pero no existe ningún mecanismo que verifique la estructura antes de que el servidor arranque.

**Fix — Validación en `initialize_db()`:**

```python
# src/meridian/db/connection.py
from pathlib import Path

REQUIRED_KB_DIRS = [
    "knowledge-base/global",
    "knowledge-base/projects",
    "lessons/global",
    "lessons/projects",
]

def initialize_db(db_path: Path) -> None:
    """Inicializa la DB y verifica que la estructura de directorios del KB exista."""
    kb_path = db_path.parent

    missing = [d for d in REQUIRED_KB_DIRS if not (kb_path / d).is_dir()]
    if missing:
        dirs_str = "\n  ".join(missing)
        raise RuntimeError(
            f"KNOWLEDGE_BASE_PATH '{kb_path}' está incompleto.\n"
            f"Directorios faltantes:\n  {dirs_str}\n\n"
            f"Ejecuta:\n"
            + "\n".join(f"  mkdir -p '{kb_path / d}'" for d in missing)
        )

    # ... resto de la inicialización existente
```

**Fix alternativo — Creación automática con advertencia:**

```python
for d in REQUIRED_KB_DIRS:
    target = kb_path / d
    if not target.is_dir():
        target.mkdir(parents=True, exist_ok=True)
        print(f"[meridian] Directorio creado: {target}", file=sys.stderr)
```

La segunda opción es más amigable para nuevos usuarios pero puede enmascarar una configuración incorrecta de `KNOWLEDGE_BASE_PATH`. Se recomienda la primera opción con un mensaje de error claro que incluya el comando de corrección.

**Fix en README:**

Agregar después de los comandos `mkdir -p` una verificación explícita:

```bash
# Verificar la estructura completa
ls ~/meridian-kb/knowledge-base/
# Debe mostrar: global/  projects/

ls ~/meridian-kb/lessons/
# Debe mostrar: global/  projects/
```

## LL-MERIDIAN-009
**Scope:** project-meridian
**Proyecto:** meridian
**Fecha:** 2026-04-20
**Severidad del impacto:** medium
**Área afectada:** installation-python-env
**Tags:** uv, venv, libpython, dyld
**Qué pasó:** El .venv creado con uv falló al cargar con dyld error: "Library not loaded: @rpath/libpython3.11.dylib". Esto ocurrió tras una actualización del sistema operativo.
**Impacto:** El servidor MCP no arrancaba. uv run fallaba silenciosamente desde la perspectiva de Claude Code (proceso terminaba con SIGABRT).
**Causa raíz:** El .venv mantiene hardcoded el RPATH del intérprete original. Al actualizar macOS, la librería dinámica quedó en una ruta diferente.
**Resolución:** Documentar uv python pin 3.11 post-clone para fijar la versión administrada por uv. Agregar sección Troubleshooting en README con rm -rf .venv && uv sync como primer remedio. Agregar check_python_environment() en __main__.py para detectar ImportError al arrancar.
**Originó regla:** RN-MERIDIAN-011
