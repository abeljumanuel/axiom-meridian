# Reporte Técnico de Auditoría — Axiom Meridian v0.1.0

**Fecha:** 2026-04-20  
**Versión auditada:** `v0.1.0`  
**Base de código:** `axiom-juma/meridian`  
**Metodología:** Revisión estática de fuentes + ejecución real de migración de conocimiento  
**Destinatarios:** Arquitecto de Software (revisión), Equipo de Desarrollo y QA (implementación)

---

## Contexto

Este reporte es resultado de la primera ejecución real del servidor Meridian sobre una base de conocimiento de producción:

- **Reglas migradas:** 13 reglas desde `Global_Rules.md` → scopes `global-quarkus`, `global-java`, `global-go`
- **Lessons migradas:** 19 lecciones desde archivos de memoria del proyecto `ms-upi-psp-integrator`
- **Herramienta de validación:** Claude Code (MCP client) sobre macOS Darwin 25.4.0

Durante la ejecución se encontraron 5 bugs bloqueantes, 3 inconsistencias de API críticas, y 34 issues adicionales clasificados por prioridad. El sistema es funcionalmente correcto en el happy path, pero requiere los ajustes descritos antes de considerarse production-ready.

## 1. Bugs Críticos

### BUG-01 — `embedding_id` se asigna con el valor incorrecto

**Severidad:** Alta  
**Archivos:** `src/meridian/tools/knowledge_management.py:1030–1032, 1085–1087`  
**Afecta:** `generate_embeddings()`

```python
# Código actual — incorrecto
conn.execute(
    "UPDATE rules SET embedding_id = ? WHERE id = ?",
    (rule_id, rule_id),  # embedding_id recibe rule_id en lugar del ID del embedding
)
```

El campo `embedding_id` de la tabla `rules` (y análogamente en `lessons`) se actualiza con el mismo valor que `id`. El propósito de este campo es almacenar el identificador del vector en ChromaDB, no el ID de la regla. Como consecuencia, no es posible saber qué reglas tienen embeddings reales generados ni cuáles están desactualizados.

**Fix propuesto:**

```python
import hashlib

embedding_hash = hashlib.sha256(str(embedding_vector)).hexdigest()[:16]

conn.execute(
    "UPDATE rules SET embedding_id = ? WHERE id = ?",
    (embedding_hash, rule_id),
)
```

El mismo fix aplica para la actualización de `lessons.embedding_id` en la línea 1085–1087.

### BUG-02 — Jerarquía de scopes puede generar bucle infinito

**Severidad:** Alta  
**Archivos:** `src/meridian/db/schema.sql:6`, `src/meridian/utils/scope_resolver.py:27–34`

El schema permite que `scope_A.parent_id = scope_B` y `scope_B.parent_id = scope_A` simultáneamente. No existe ningún constraint de base de datos ni lógica en el resolver que detecte ciclos. Si esto ocurre, `resolve_scope_hierarchy()` itera indefinidamente y el servidor MCP se cuelga sin emitir error.

**Fix propuesto — detección de ciclos en el resolver:**

```python
def resolve_scope_hierarchy(conn, scope_id: str) -> list[str]:
    visited = set()
    chain = []
    current = scope_id
    while current:
        if current in visited:
            raise ValueError(f"Circular scope hierarchy detected at '{current}'")
        visited.add(current)
        chain.append(current)
        row = conn.execute(
            "SELECT parent_id FROM scopes WHERE id = ?", (current,)
        ).fetchone()
        current = row[0] if row else None
    return chain
```

**Fix adicional en schema** — agregar validación de profundidad máxima via trigger, o documentar explícitamente que la gestión de scopes es responsabilidad del administrador.

### BUG-03 — `strip_private_tags()` rompe el contrato de tipo

**Severidad:** Media  
**Archivo:** `src/meridian/utils/privacy.py:12–15`

```python
def strip_private_tags(text: str) -> str:
    if text is None:
        return None  # type annotation dice str, retorna None
```

Cualquier caller que confíe en la anotación `-> str` y llame `.lower()` u otro método de string sobre el resultado obtiene un `AttributeError` en runtime que no aparece en análisis estático.

**Fix:**

```python
def strip_private_tags(text: str | None) -> str | None:
    if text is None:
        return None
    ...
```

O bien, si `None` nunca debe entrar a esta función, cambiar a:

```python
def strip_private_tags(text: str) -> str:
    if not isinstance(text, str):
        raise TypeError(f"Expected str, got {type(text).__name__}")
    ...
```

### BUG-04 — Tabla `lessons` faltaba 4 columnas en `schema.sql`

**Severidad:** Alta (bloqueante para aprobación de lessons)  
**Archivo:** `src/meridian/db/schema.sql:70–89`  
**Estado:** **Corregido en esta sesión**

Las columnas `source_type`, `source_ref`, `created_at`, `updated_at` existían en el código Python de `knowledge_management.py` pero no en el DDL de la tabla `lessons`. La aprobación de cualquier lesson fallaba con:

```
sqlite3.OperationalError: table lessons has no column named source_type
```

**Corrección aplicada al schema.sql:**

```sql
CREATE TABLE lessons (
  ...
  source_type       TEXT,
  source_ref        TEXT,
  ...
  created_at        TEXT DEFAULT (datetime('now')),
  updated_at        TEXT DEFAULT (datetime('now'))
);
```

**Script de migración para bases de datos existentes** (debe incluirse como `migrations/001_lessons_columns.sql`):

```sql
ALTER TABLE lessons ADD COLUMN source_type TEXT;
ALTER TABLE lessons ADD COLUMN source_ref TEXT;
ALTER TABLE lessons ADD COLUMN created_at TEXT DEFAULT (datetime('now'));
ALTER TABLE lessons ADD COLUMN updated_at TEXT DEFAULT (datetime('now'));
```

**Recomendación:** Implementar un sistema de migraciones versionadas (similar a Flyway o Liquibase, o una versión minimalista con tabla `schema_version`) para que la diferencia entre el schema en disco y el DDL en código sea detectada al arrancar.

### BUG-05 — `lesson_history` no registra el contenido del cambio

**Severidad:** Media  
**Archivo:** `src/meridian/db/schema.sql:59–67`

La tabla `rule_history` tiene columnas `previous_text` y `new_text` que permiten un diff completo de cada cambio a una regla. `lesson_history` no tiene estas columnas: solo registra que el cambio ocurrió, no qué cambió.

**Fix — agregar al schema:**

```sql
CREATE TABLE lesson_history (
  id            TEXT PRIMARY KEY,
  lesson_id     TEXT NOT NULL REFERENCES lessons(id),
  change_type   TEXT NOT NULL,
  previous_text TEXT,    -- agregar
  new_text      TEXT,    -- agregar
  reason        TEXT,
  triggered_by  TEXT,
  changed_at    TEXT DEFAULT (datetime('now'))
);
```

Y poblar ambos campos en el flujo de aprobación/actualización de lessons en `knowledge_management.py`.

## 2. Inconsistencias de API

### API-01 — `query_lessons()` no acepta parámetro `conn`

**Archivo:** `src/meridian/tools/knowledge_consumption.py:224–231`

`query_rules()` acepta `conn: sqlite3.Connection | None = None` para reutilizar una conexión existente. `query_lessons()` siempre abre y cierra su propia conexión. Esta asimetría impide operar ambas funciones dentro de una misma transacción y es inconsistente para callers internos como `skill_generator.py`.

**Fix:** Homogeneizar la firma de todas las funciones de consumo:

```python
def query_lessons(
    project_id: str,
    area: str | None = None,
    tags: str | list[str] | None = None,
    query_text: str | None = None,
    format: str = "json",
    detail: str = "summary",
    conn: sqlite3.Connection | None = None,  # agregar
) -> str:
    close_on_exit = conn is None
    if conn is None:
        conn = get_connection(get_db_path())
    try:
        ...
    finally:
        if close_on_exit:
            conn.close()
```

Aplicar el mismo patrón a `get_rule_context`, `get_rule_timeline`, `get_project_scope_resolution`, `get_rule_audit_log`.

---

### API-02 — Clave `id` vs `proposal_id` inconsistente entre funciones

**Archivos:** `tools/knowledge_management.py`, `tools/knowledge_consumption.py`

| Función | Clave retornada |
|---------|----------------|
| `list_pending_proposals()` | `id` |
| `convert_to_atomic_format()` | `proposal_id` |
| `approve_proposal()` | `code` (del resultado) |

Un caller que itera la respuesta de `convert_to_atomic_format()` esperando `proposal_id` y luego intenta aprobar con esa clave falla con `KeyError` al llamar `list_pending_proposals()`, que devuelve `id`. Esto fue la causa del error observado en la sesión de migración.

**Fix:** Estandarizar a `id` en todos los retornos que representen el identificador de una propuesta. Actualizar `convert_to_atomic_format()` para retornar `id` en lugar de `proposal_id`.

---

### API-03 — `project_id` requiere prefijo `project-` sin validación ni documentación

**Archivo:** `src/meridian/utils/scope_resolver.py:22`

Llamar `query_rules(project_id='psp-integrator')` lanza:

```
ValueError: Scope 'psp-integrator' not found.
Valid scopes: ['global', 'global-java', ..., 'project-psp-integrator']
```

El prefijo `project-` es requerido por el resolver, pero ningún tool lo valida ni lo normaliza antes. El mensaje de error del resolver sí lista los scopes válidos, lo cual es positivo, pero el comportamiento ideal es que el tool acepte ambas formas.

**Fix — normalización defensiva en el resolver:**

```python
def resolve_scope_hierarchy(conn, project_id: str) -> list[str]:
    # Normalizar: si el ID no existe pero "project-<id>" sí, usarlo
    row = conn.execute("SELECT id FROM scopes WHERE id = ?", (project_id,)).fetchone()
    if row is None:
        candidate = f"project-{project_id}"
        row = conn.execute("SELECT id FROM scopes WHERE id = ?", (candidate,)).fetchone()
        if row:
            project_id = candidate
        else:
            valid = [r[0] for r in conn.execute("SELECT id FROM scopes").fetchall()]
            raise ValueError(f"Scope '{project_id}' not found. Valid scopes: {valid}")
    ...
```

## 3. Schema SQL — Gaps y Correcciones

### SCHEMA-01 — Sin constraints CHECK en columnas `status`

Las columnas `rules.status` y `lessons.status` tienen `DEFAULT 'active'` pero no validan los valores permitidos. Código disperso en la codebase usa `'active'` y `'deprecated'`, pero nada impide insertar `'ACTIVE'`, `'deleted'`, u otro valor inválido.

**Fix:**

```sql
status TEXT DEFAULT 'active' CHECK (status IN ('active', 'deprecated'))
```

---

### SCHEMA-02 — Timestamps sin precisión subsegundo

Todos los campos de timestamp usan `datetime('now')` con precisión de 1 segundo. Dos operaciones en el mismo segundo quedan sin orden cronológico definido en el audit log y en `rule_history`.

**Fix:**

```sql
-- Reemplazar datetime('now') por:
strftime('%Y-%m-%dT%H:%M:%f', 'now')
-- Ejemplo: 2026-04-20T18:32:45.123
```

---

### SCHEMA-03 — `id` de reglas y lessons es igual al `code`

El primary key `id` de la tabla `rules` se puebla con el código canónico (e.g., `RN-JAVA-001`). Si en el futuro el formato de código cambia, todas las foreign keys referenciando ese `id` se rompen. `UNIQUE` en `code` ya garantiza unicidad; el `id` debería ser un UUID o un serial independiente.

**Fix a evaluar:** Separar `id` (UUID) de `code` (código canónico). Es un breaking change, requiere migración de datos.

## 4. Ciclo de Vida de Lessons

Existe una asimetría fundamental entre el ciclo de vida de reglas y lessons:

| Operación | Rules | Lessons |
|-----------|:-----:|:-------:|
| Crear via propuesta | ✓ | ✓ |
| Editar propuesta pendiente | ✓ | ✓ |
| Aprobar | ✓ | ✓ |
| Rechazar | ✓ | ✓ |
| Deprecar activa | ✓ `promote_rule()` | **✗ falta** |
| Actualizar activa directamente | **✗ falta** | **✗ falta** |
| Historial de cambios con diff | ✓ | ✗ (BUG-05) |

**Implementaciones requeridas:**

```python
# 1. Deprecar una lesson
def deprecate_lesson(lesson_id: str, reason: str | None = None) -> dict:
    """Marca una lesson como deprecated y registra en lesson_history."""

# 2. Actualizar una regla activa directamente
def update_rule(rule_id: str, new_text: str, metadata: dict | None = None) -> dict:
    """Actualiza el texto de una regla aprobada y registra el cambio en rule_history."""
```

## 5. Calidad del Parser Legacy

El parser legacy (`src/meridian/parsers/legacy_parser.py`) es funcional para el caso base pero presenta limitaciones que afectan la calidad de las propuestas generadas.

### PARSER-01 — Pérdida de metadata custom

El parser extrae la sección completa como `proposed_text` pero solo mapea `Category` y `Severity` como metadata estructurada. Cualquier campo adicional (`**Fuente:**`, `**Contexto:**`, `**Aplica a:**`) se incluye en el texto pero no se indexa como atributo consultable.

**Impacto:** Las propuestas migradas desde archivos legacy tienen `category: "general"` y `tags: []` aunque el texto original contenga información más específica.

**Fix:** Ampliar el parser para extraer todos los pares `**Clave:** Valor` y almacenarlos en `metadata`.

---

### PARSER-02 — Sin deduplicación de propuestas

Si `convert_to_atomic_format()` se ejecuta dos veces sobre el mismo archivo, crea propuestas duplicadas en `pending_proposals`. No existe ningún check de idempotencia.

**Fix:**

```python
# Antes de insertar, verificar si ya existe una propuesta con el mismo hash de texto
text_hash = hashlib.sha256(proposed_text.encode()).hexdigest()
existing = conn.execute(
    "SELECT id FROM pending_proposals WHERE text_hash = ? AND status = 'pending'",
    (text_hash,)
).fetchone()
if existing:
    continue  # skip duplicado
```

Requiere agregar columna `text_hash TEXT` a `pending_proposals`.

---

### PARSER-03 — Inferencia de scope incompleta

El parser infiere el scope por keywords en el texto:

| Keyword | Scope inferido |
|---------|---------------|
| `quarkus` | `global-quarkus` |
| `java` | `global-java` |
| `nestjs` | `global-nestjs` |
| `go` | `global-go` |
| `flutter` | `global-flutter` |

Scopes registrados en schema pero sin inferencia: `global-spring-boot`, `global-go-fiber`, `global-go-gin`.

**Fix:** Completar el mapa de keywords en `convert_to_atomic_format()`.

## 6. Gaps de CLI

El módulo `__main__.py` expone únicamente:

```
python -m meridian version
python -m meridian mcp
python -m meridian serve [PORT]
```

Para que el proyecto sea operable sin escribir scripts Python ad-hoc, se propone la siguiente interfaz CLI:

```
python -m meridian db init
    Inicializa la base de datos en KNOWLEDGE_BASE_PATH.

python -m meridian migrate rules <file> --scope <scope_id>
    Convierte un archivo legacy a propuestas. Equivale a convert_to_atomic_format(doc_type='rules').

python -m meridian migrate lessons <file> --scope <scope_id>
    Equivale a convert_to_atomic_format(doc_type='lessons').

python -m meridian proposals list [--status pending|approved|rejected]
    Lista propuestas pendientes.

python -m meridian proposals approve <id>
    Aprueba una propuesta individual.

python -m meridian proposals approve --all
    Aprueba todas las propuestas pendientes (requiere confirmación interactiva).

python -m meridian query rules --project <project_id> [--category <cat>] [--severity <sev>]
    Consulta reglas desde la línea de comandos.

python -m meridian query lessons --project <project_id> [--area <area>]
    Consulta lessons desde la línea de comandos.
```

**Nota sobre macOS:** El comando `python` no está disponible en macOS por defecto. Todos los ejemplos en documentación y CLI deben usar `uv run python` o documentar explícitamente el requisito de `python3` en PATH.

## 7. Seguridad

### SEC-01 — Access control bypasseable desde Python directo

**Archivo:** `src/meridian/server.py` + `src/meridian/tools/knowledge_management.py`

El chequeo de `MERIDIAN_ACCESS_LEVEL` ocurre únicamente en `server.py` antes de despachar la llamada al tool. Si alguien importa directamente `from meridian.tools.knowledge_management import approve_proposal`, el control de acceso no se ejecuta.

**Recomendación para el arquitecto:** Decidir si las funciones del módulo `tools/` son API pública o interna. Si son internas, renombrarlas con prefijo `_` y documentar que el único entry point soportado es el servidor MCP. Si deben ser usables directamente, mover la validación de acceso dentro de cada función.

---

### SEC-02 — Audit log omite huellas de contenido sensible

**Archivo:** `src/meridian/utils/security.py:103–104`

Los campos `pr_diff`, `feedback_text`, `text`, `proposed_text`, `new_text` se omiten completamente del log de auditoría. Si bien es correcto no loguear el contenido completo, omitir toda huella impide correlacionar operaciones en una investigación de incidentes.

**Fix:** Incluir un hash truncado:

```python
"proposed_text_sha256": hashlib.sha256(proposed_text.encode()).hexdigest()[:12]
```

---

### SEC-03 — HTTP/SSE: token generado pero no validado

**Archivo:** `src/meridian/server.py` (modo HTTP)

En modo HTTP/SSE, el servidor imprime un token al arrancar pero FastMCP no implementa la validación de ese token en los requests entrantes. Cualquier cliente que conozca la URL puede invocar tools sin autenticación.

**Impacto:** Solo aplica al modo HTTP. El modo stdio (usado por Claude Code) no tiene este problema.

**Fix:** Implementar middleware de validación de `Authorization: Bearer <token>` antes de despachar al servidor MCP, o documentar explícitamente que el modo HTTP requiere un reverse proxy con autenticación externa.

## 9. Cobertura de Tests

### Gaps identificados

**Tests unitarios faltantes:**

- `parsers/atomic_parser.py`: No hay test para campos multiline (e.g., `**Regla:**` con 3+ líneas).
- `utils/scope_resolver.py`: No hay test para scopes con ciclos ni para scopes inexistentes.
- `utils/privacy.py`: No hay test para input `None`.

**Tests de integración faltantes:**

- Flujo completo de error: aprobar propuesta inexistente, aprobar con archivo destino faltante.
- Matrix de access control: verificar que cada tool rechaza correctamente un nivel insuficiente.
- Idempotencia: ejecutar `convert_to_atomic_format()` dos veces sobre el mismo archivo y verificar ausencia de duplicados (actualmente crea duplicados — PARSER-02).

**Test de regresión recomendado:**

Agregar un test de smoke que ejecute el flujo completo:
1. `initialize_db()`
2. `convert_to_atomic_format()` sobre un archivo de muestra
3. `list_pending_proposals()`
4. `approve_proposal()` para cada propuesta
5. `query_rules()` y verificar que retorna resultados

Este test cubre la ruta de ejecución real y habría detectado BUG-04 antes del release.

## 10. Carga del Propio Proyecto como Conocimiento

Estos documentos son candidatos directos para ser indexados en el propio servidor, creando un caso de uso de auto-referencia: *Meridian gestiona el conocimiento sobre Meridian*.

### Preparación

**Paso 1 — Crear el scope del proyecto:**

```sql
INSERT INTO scopes VALUES ('project-meridian', 'project', 'Meridian MCP Server', 'global-python');
INSERT INTO scope_attributes VALUES ('project-meridian', 'framework', 'python');
INSERT INTO scope_attributes VALUES ('project-meridian', 'component_role', 'mcp-server');
INSERT INTO scope_attributes VALUES ('project-meridian', 'runtime_version', 'python-3.11');
```

Nota: Requiere que exista el scope `global-python` o usar `global` como parent.

**Paso 2 — Crear archivos de destino:**

```bash
touch ~/meridian-kb/knowledge-base/projects/meridian.md
touch ~/meridian-kb/lessons/projects/meridian.md
```

**Paso 3 — Indexar los ADRs como reglas de diseño:**

```bash
KNOWLEDGE_BASE_PATH=~/meridian-kb MERIDIAN_ACCESS_LEVEL=write uv run python - << 'EOF'
from meridian.tools.knowledge_management import convert_to_atomic_format
import json

for filepath in ['ADR-001-response-serialization-format.md',
                 'ADR-002-dynamic-context-attributes.md']:

```

**Paso 4 — Cargar los issues de este reporte como lessons:**

```bash
KNOWLEDGE_BASE_PATH=~/meridian-kb MERIDIAN_ACCESS_LEVEL=write uv run python - << 'EOF'
from meridian.tools.knowledge_management import convert_to_atomic_format
import json

result = convert_to_atomic_format(
    filepath='changes/test-20160420.md',
    default_scope_id='project-meridian',
    doc_type='lessons'

print(json.dumps(result, indent=2))
EOF
```
